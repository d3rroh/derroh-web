Migrating from Docker Compose to k3s: What Actually Breaks

k3s kubernetes docker-compose nginx-ingress

Migrating a full production stack — derroh-web, docker-mailserver, kimberley-web, n8n, and more — from Docker Compose to a k3s cluster on a bare Contabo VPS looked straightforward on paper. In practice, several assumptions from the Compose world didn't carry over cleanly.

Port Conflicts

Compose services binding directly to host ports don't translate 1:1 into Kubernetes. Every service needed to be rethought as a ClusterIP Service behind an Ingress, rather than assuming a direct host-port mapping — which meant auditing every port binding in the original Compose files before writing a single manifest.

CNI Surprises

On a single-node bare VPS, the default CNI behavior isn't always what you'd expect coming from Compose's simpler bridge networking. Pod-to-pod communication that "just worked" in Compose needed explicit verification once workloads moved into k3s's networking model.

LoadBalancer Gotchas

Standard Kubernetes LoadBalancer services expect a cloud provider to hand out an external IP — which doesn't exist on a bare VPS. The clean path was routing everything through nginx-ingress as the ingress controller, with Cloudflare handling SSL/CDN in front of the single VPS IP, rather than fighting Kubernetes for cloud-native load balancing it can't actually provide here.

Takeaway

For a single-node bare-metal-style cluster, nginx-ingress + Cloudflare is the pragmatic setup — it avoids the LoadBalancer problem entirely and gives you SSL termination and CDN for free.
