Kubernetes PVC Permissions: fsGroup, Init Containers, and www-data

kubernetes pvc laravel fsgroup

Laravel storage permission errors are one of the most common headaches when moving a PHP app onto a Kubernetes PersistentVolumeClaim. The web server runs as www-data, but volumes mounted into a pod don't automatically carry the right ownership.

The fsGroup Fix

Setting fsGroup: 33 (the standard www-data GID on Debian-based images) in the pod's securityContext tells Kubernetes to change group ownership of the mounted volume to match, so the web server process can actually write to storage/ and bootstrap/cache/ without manual chown steps.

When fsGroup Isn't Enough

On some storage backends, fsGroup alone doesn't retroactively fix ownership on a volume that already has files with the wrong permissions. In those cases, an init container running as runAsUser: 0 that does an explicit chown -R pass before the main container starts is the reliable fallback.

Making It Self-Healing

The last piece is making sure the container's entrypoint script re-asserts correct permissions on every startup rather than assuming they'll persist — so a pod restart, rescheduling to a different node, or a fresh PVC mount doesn't reintroduce the same permission errors.
